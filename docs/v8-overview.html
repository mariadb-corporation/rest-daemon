Replacing GraalVM with V8 as the script engine

Proposal, not decided · 2026-10-30

The JIT executor plugin runs MRS scripts on GraalJS inside a GraalVM native image. This page collects what we found out on 30 October 2026 about moving it to V8: why, what it touches, how debugging and TypeScript keep working, where V8 would come from, and a phased plan with estimates. The plan itself is docs/v8-plan.md.

Why move

The move to GraalVM was made for non-technical reasons, and the MRS scripts use nothing that is specific to GraalJS. Four things argue for V8 now.

Platforms

GraalVM Community has never shipped a Windows ARM64 build, and none is planned. The request (oracle/graal#9215, open since 2024, "help wanted") got the answer "not on our roadmap" from the GraalVM team in January 2026. GraalVM also dropped macOS x64 after 25.0.0: our pinned 23.0.1 still has it, but the next upgrade would cost us the macOS x64 package.

Build

The JIT executor library is a GraalVM native image: a Maven build, a 20 GB heap for native-image, minutes per platform, and 2,653 lines of patches on GraalVM's polyglot native API in ext/polyglot. With V8 the plugin links a prebuilt static library that is pinned by version and checksum.

Licensing

The GraalVM, OpenJDK and GraalJS notices are the bulk of the LICENSE file and were the hardest part of legal's review (section B.1). V8 is BSD-3 with a short list of third-party notices. The written offer for source code can stay; it is cheap and covers the MySQL-derived GPL code regardless.

Debugging

Unchanged in substance. VS Code attaches to the engine over the Chrome DevTools Protocol, and V8's inspector is that protocol's reference implementation. Details below.

Windows on ARM today

The release build has six legs, but only five distinct packages. The windows-arm64 leg compiles the x64 daemon on an ARM64 runner (vcvarsall arm64_amd64) with the x64 GraalVM library under emulation. Its package is another windows-x64.zip, and Publish Release takes the one from the x64 leg. The leg exists to prove that the x64 build works on an ARM64 development machine; the published x64 package runs on Windows on ARM under emulation, and verification tests exactly that on a Windows ARM runner.

A real ARM64 daemon with the x64 GraalVM library is not possible: a native ARM64 process cannot load an x64 DLL. Only ARM64EC binaries can, and that would mean building Connector/C, OpenSSL and ICU as ARM64EC through vcpkg, which is large and uncertain. So with GraalVM the options are: keep the x64 package (recommended today), publish the same binaries under an arm64 name (misleading), or ship a native ARM64 daemon without the JIT executor (no MRS scripts).

How debugging works, with either engine

The shell plugins' mrs_scripts example attaches with VS Code's built-in Node.js debugger: "type": "node", "request": "attach", "port": 9229. That debugger speaks the Chrome DevTools Protocol (CDP) to the engine. Nothing in the chain is GraalVM-specific.

With V8 we write no protocol messages. We write what every program embedding V8 writes: an inspector client that passes messages between the socket and the inspector session, registers each script context, and runs a message loop while a script is paused on the execution thread; plus a small WebSocket server on the debug port with the two discovery endpoints js-debug uses. GraalVM's inspector also opens its own port, so the daemon's HTTP server is not involved. A debug adapter of our own (DAP directly) would rebuild what js-debug already does and gain nothing; CDP also keeps the daemon debuggable from Chrome DevTools.

TypeScript source maps

Getting source maps to work with GraalJS took effort, so the natural worry is that V8 brings the same fight back. It does not: the map handling lives in VS Code's debugger, not in the engine, and V8 is the engine that debugger is built for.

The scripts do not exist as files on the developer's machine in the form the engine runs them. The daemon loads them from the content set in the database through its own virtual file system (mrs/file_system/db_service_file_system.cc), and the inspector reports each script under its content-set path, such as /myService/scripts/build/MrsScriptModule.js. VS Code then has to do two things on its own:

  1. find the .map file named by the script's //# sourceMappingURL= comment, and
  2. map the sources inside it to files in the workspace.

Step 2 is what the workaround in the example's rollup.config.mjs fixes: it forces sourceRoot to the absolute project folder so the map's sources resolve to local files. The blanked resolveSourceMapLocations and the "trace": true in the launch config are leftovers of the same fight. This is a consequence of scripts living in the database and is identical with V8.

What V8 adds: the daemon implements module loading itself, so it decides each script's name and can set the source-map URL explicitly when compiling (ScriptOrigin), for example to the map's HTTPS URL in the content set, which VS Code fetches directly. The GraalVM-specific Windows backslash quirk the daemon has to undo today goes away with it.

Independent of the engine: have rollup emit inline source maps (sourcemap: 'inline') for development builds. The map travels inside the script as a data: URL, VS Code decodes it without looking for a file, and step 1 disappears today, with GraalJS. The forced sourceRoot stays needed for step 2.

What stays and what changes

The engine sits behind one interface, and the REST service plugin uses only it, in six files: JitExecutorComponent::get_context, IContext::execute, ServiceHandlerConfig, GlobalCallbacks and IFile_system. That interface stays, so the REST service plugin, its tests, the content-set file system and the _debug handler do not change. The script contract (mrs.d.ts: print, SqlError, Session.runSql, getSession, getCurrentMrsUserId, getContentSetPath; ES modules; promises resolved; JSON or raw results) stays too.

Inside src/jit_executor (21,000 lines without tests), 18 files call GraalVM's poly_* API. The rest, above all jit_executor_value.cc (1,972 lines, the value model), the database/ layer and utils/, is engine independent.

Where V8 comes from

Building V8 from source needs depot_tools, gn and ninja and takes one to two hours per platform. Prebuilt static monoliths are the practical route, cached in CI by version as the JIT library is today.

SourceVersionLinux x64Linux arm64macOS x64macOS arm64Windows x64Windows arm64
kassane/libv8 (default, i18n, pointer-compression variants; SHA256SUMS)15.1.46, Jun 2026yesyesnoyesyesyes
zyedidia/v8-build14.0.365, Jan 2026yesyesnoyesyesyes
vcpkg v8 port9.1.269, 2021not usable

So macOS x64 needs a build of our own (a GitHub macos-15-intel runner, cached by version) or is dropped. GraalVM would force the same choice at its next upgrade.

Toolchain check first. V8's default build uses its own clang and libc++ (use_custom_libcxx=true), which does not link against our libstdc++ build in the Rocky 9 container; on Windows the CRT flavour (/MD) must match ours. The spike settles this before anything else; the fallback is our own build with use_custom_libcxx=false.

Phases

About 8–11 weeks of one engineer, plus legal's turnaround on the LICENSE. V1 and V2 are the bulk; the debugger is the smallest part.

  1. Spike1 week
    • Link the prebuilt V8 on macOS arm64 and Linux x64 (Rocky 9); confirm the toolchain questions and the Windows arm64 link with our MSVC.
    • Run one content-set script end to end with a minimal engine: module load from IFile_system, getSession().runSql(), promise result, timeout.
    • Attach VS Code once to a hand-written WebSocket loop to confirm the pause loop on the execution thread.
    • Choose the variant: i18n (keeps Intl, as GraalJS has it via ICU4J; adds icudtl.dat, about 10 MB) or default.
    Exit: go/no-go with the toolchain answers and the chosen V8 source.
  2. Engine core2–3 weeks
    • src/jit_executor/src/v8/: isolate and context lifecycle, pool, execution thread with queue, timeouts and termination, promise resolution, ES modules and dynamic import() from the content set, error mapping with guest stack traces, print and the four global functions.
    • Memory limits: max_heap_size, maximum_ram_size, memory_units on HeapStatistics.
    Exit: scripting_base_tests and scripting_multi_service pass on macOS.
  3. Object bridge and types2 weeks
    • Session, Result, Row, Column, Date on templates; value conversion both ways including BigInt, Date, binary and nested arrays/objects; weak handles for collectable natives.
    Exit: scripting_type_bridging passes; the MRS suite passes on Linux, macOS and Windows x64. Golden .result files that quote engine error messages are updated deliberately.
  4. Debugger1–2 weeks
    • V8InspectorClient and Channel; one inspector session per debug context; runMessageLoopOnPause on the execution thread; no timeout while debugging, as today.
    • WebSocket server on the debug port: /json/version, /json/list, RFC 6455 upgrade. Hand-written (a few hundred lines) or ixwebsocket (BSD-3, in vcpkg).
    • Keep the debug-context semantics: get_context(debug_port), release_debug_context, stop_debug_context, the _debug toggle.
    Exit: the mrs_scripts launch config attaches unchanged; breakpoints in .ts sources bind through source maps; stepping and variables work; Chrome DevTools attaches too.
  5. Build, CI, packaging, LICENSE1–2 weeks
    • bootstrap_v8.cmake replaces bootstrap_jit_executor.cmake; WITH_JIT_EXECUTOR / MRS_JIT_EXECUTOR_LIB keep their meaning for the release workflow's cache.
    • Release workflow: a native windows-arm64 leg; a decision on macOS x64. verify_package.sh: no libjitexecutor, the plugin loads, a script runs.
    • LICENSE: remove the GraalVM, OpenJDK and GraalJS sections; add V8 and its third-party notices. Legal reviews the result.
    Exit: all packages built and verified; LICENSE cleared.
  6. Cutover and cleanup1 week
    • Remove ext/polyglot, the polyglot_* sources, the GraalVM download; update README, PLAN.md, PROGRESS.md, PROJECT_CONTEXT.md.
    • Tag the last GraalVM commit and keep it as the fallback until the first V8 release has run for a cycle.
    Exit: first pre-release with V8; packages show no GraalVM.

Decisions needed before the spike

  • Go ahead with the spike at all.
  • i18n variant (full Intl, matches GraalJS) or default.
  • V8 source: kassane/libv8 as is, or our own CI builds from the start.
  • macOS x64: own V8 build, or drop the package.
  • WebSocket transport: hand-written, or ixwebsocket.
